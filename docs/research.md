# Исследовательское задание T2

## Конвейер «эксперимент → артефакт → страница»

Результат вычислительного эксперимента можно перенести на сайт несколькими способами. Для этой работы сравниваются четыре подхода, указанные в задании.

| Подход | Как работает | Плюсы | Минусы | Когда использовать |
|---|---|---|---|---|
| Статические изображения вручную | График заранее сохраняется в PNG/SVG и добавляется в Markdown | Самый простой способ, сборка почти ничего не вычисляет | Легко опубликовать устаревший результат; слабая воспроизводимость | Редко меняющиеся готовые результаты |
| `nbconvert` / MyST-NB / Quarto | Ноутбук исполняется или преобразуется во время подготовки сайта | Код, текст и результат находятся рядом | Сборка становится тяжелее; окружение сложнее | Небольшие и средние notebook-эксперименты |
| `papermill` | Ноутбук запускается с набором параметров и сохраняется как отдельный артефакт | Удобно воспроизводить серии параметризованных запусков | Для простой задачи добавляет лишний слой | Серии однотипных notebook-экспериментов |
| Python-скрипт перед MkDocs | Скрипт читает данные и создаёт Markdown/CSV/PNG, после чего MkDocs собирает сайт | Простая архитектура, легко отлаживать, нет notebook-зависимостей | Нужно явно определить формат генерируемых файлов | Небольшой воспроизводимый проект, как в этой работе |

### Выбранный вариант

Для практической части выбран отдельный Python-скрипт, запускаемый перед MkDocs. Это минимальная цепочка:

```text
CSV → generate.py → Markdown + PNG → MkDocs → статический HTML
```

Она проще notebook-конвейера и при этом сохраняет связь исходных данных, кода расчёта и опубликованного результата.

## Где проводить вычисления

Границу между вычислениями в CI и предварительным расчётом удобно проводить по стоимости эксперимента.

**В CI разумно выполнять вычисления**, если они быстро завершаются на обычном CPU, требуют умеренный объём памяти и легко воспроизводятся из файлов репозитория. Например, агрегация CSV и построение нескольких графиков.

**Отдельно от CI лучше выполнять вычисления**, если нужны часы работы, GPU, очень большой датасет или дорогой внешний ресурс. В таком случае CI получает уже готовые артефакты и только собирает сайт.

Для готового артефакта следует хранить связь с экспериментом: commit кода, версию или хеш датасета, дату запуска и параметры эксперимента. В этой работе эта идея реализована через commit, дату сборки и SHA-256 CSV.

## Ограничения CI на примере GitHub Actions

На стандартном GitHub-hosted runner один job может выполняться до 6 часов. Стандартные runners не являются GPU-runners; GPU доступен в категории larger runners. Для кэша действует отдельное хранилище репозитория, по умолчанию 10 ГБ. Лимиты минут и артефактного хранилища зависят от тарифа; для публичных репозиториев стандартные GitHub-hosted runners доступны без оплаты минут.

Для нашей лабораторной эти ограничения несущественны: CSV мал, расчёт выполняется на CPU за секунды, а итоговый сайт занимает значительно меньше лимитов GitHub Actions.
